# Cleaned corpus audit — 16 September 2026

## Decision

**The current corpus can support pipeline prototyping, but should not yet be frozen
as the input for the research comparison.** The first cleaning pass preserved source
traceability and much of the extractable text. It did not consistently resolve page
noise, reading order, heading structure, table semantics, mathematical layout or
text embedded in images. These problems can confound comparisons of chunking methods.

No cleaner or corpus content was changed during this audit. Audit artifacts were
saved under `data/outputs/cleaning_audit_2026-09-16/`; the existing integrity validator
was rerun successfully. Its generated validation report was refreshed.

## What was checked

- Whole-corpus integrity: all 60 sources and 6,215 page records; source hashes,
  output hashes, JSON/text agreement and page offsets passed again.
- Whole-corpus formatting counts: scan of all saved page `clean_text` fields.
- Visual inspection: **20 source PDF pages across 10 PDFs**, compared with the
  corresponding cleaned output. Source pages were rendered and actually inspected,
  rather than trusting one extractor's text as ground truth.
- Selection: the two PDFs open in the user's IDE plus eight seeded random PDFs,
  stratified across members (3 Aysha, 4 Haleema including the two fixed files,
  3 Vithusan). Seed: `20260916`. For each PDF, one page was randomly selected from
  physical page 5 onward and a second page was selected preferentially from pages
  with table/reading-order flags. In one file without those flags, the second page
  came from the remaining pages. This deliberately includes difficult layouts.

This is a diagnostic sample, **not** a statistically representative estimate of
corpus correctness. Page numbers below are one-based physical PDF pages, which can
differ from the number printed on the page. Findings apply to the inspected pages,
not every page of a listed PDF.

Remediation categories for these 20 inspected pages: **8 routine text/formatting
cleanup, 11 structure or mathematical-layout repairs, 1 missing-evidence case**.
These are reviewer judgments for this diagnostic sample, not percentages of
correct words, correct facts, or ready documents. Even the routine category needs
the formatting/heading policy applied before the experimental dataset is frozen.

### Three particularly useful counterexamples

1. **A score of 100% text retention can still hide major omissions.** FOCP page 15
   records `token_coverage: 1.0`, yet its high-level/low-level-language comparison
   table is absent. Both the reference extractor and final text omitted the image.
   OCR/visual-content review must include pages with some text, not just empty pages.
2. **No quality flag does not mean a clean page.** UW Science 2018 page 22 has no
   flags, but contains spaced decimal numbers and a displaced period. The current
   token-count check ignores punctuation and order, so it cannot catch these errors.
3. **Preserving mathematical characters does not preserve the equation.** UOM FIT
   page 36 retains SGPA, sums and variables, but not the fraction bar. A linear text
   representation needs an explicit division/grouping or a verified mathematical
   representation to convey the original equation.

The UW Science 2018 page 41 source itself states minimum 15 in one place and 16 in
another. That inconsistency is not introduced by the cleaner and must not be
silently 'corrected' during cleaning.

## What the percentages do and do not mean

| Measured property | Result | Interpretation |
|---|---:|---|
| PDFs successfully processed | 60/60 = 100% | File-processing completeness, not content accuracy. |
| Page records accounted for | 6,215/6,215 = 100% | Includes pages without extracted text. |
| Pages with an automatic review flag | 4,365/6,215 = 70.23% | Review signals, not 70.23% incorrect. |
| Pages without those flags | 1,850/6,215 = 29.77% | Not automatically verified as correct. |
| Pages containing whole-page fallback fences | 3,310/6,215 = 53.26% | Relevant to formatting consistency and header-based chunking. |
| Pages using original-text fallback | 473/6,215 = 7.61% | Retained text can preserve extraction defects and ordering issues. |
| Pages with no extractable text | 83/6,215 = 1.34% | Some may be blank; others need OCR/visual review. |
| Number-only cleaned pages | 32 | Potentially useless standalone page-number content; inspect source before excluding. |

There is **no defensible overall 'cleaning accuracy out of 100' yet**. The first
pipeline's 99% threshold is word-token retention relative to a machine extraction,
not accuracy against the visible PDF. In the original-text fallback it can be 100%
by construction. Passing unit tests and integrity checks does not change that.

For a meaningful accuracy measure, define the unit (characters, words, facts,
table cells, or pages), create reviewed reference transcriptions/evidence records,
use a representative sample across layout types, score omissions and alterations
including structure, and report uncertainty. A second team reviewer should verify
the annotations. Preserve this diagnostic sample as regression cases, but use a
separate sample to estimate performance after repairs.

## Asterisks and triple backticks

- `**heading**` is Markdown bold; it is not inherently corrupted text.
- Opening triple backticks followed by `text` and closing triple backticks are
  artificial code-block fences inserted by `fenced_layout()` around fallback pages.
  They preserve spacing for display, but should not describe ordinary handbook
  content as code in the final experimental representation.
- Some stars are actual evidence: the inspected Zoology page says `Biology*/
  Biology**`. Other stars can denote footnotes, compulsory courses, multiplication
  or programming operators. Do not globally delete `*` or all punctuation.
- Headings must be represented consistently, not sometimes `#`, sometimes bold,
  and sometimes plain text inside a fence. The existing font-based heading candidates
  are useful hints, not validated section boundaries.

A local check of the installed `MarkdownHeaderTextSplitter` produced two sections
with heading metadata for normal `#`/`##` headings, but one block with empty heading
metadata when the same input was enclosed in a `text` fence. This is a concrete risk
for the planned structure-aware method. Header-based splitting uses Markdown
headings as documented in the [LangChain guide](https://docs.langchain.com/oss/python/integrations/splitters/markdown_header_metadata_splitter).
The fence behavior was checked directly in this project's installed library.

## Which file should feed the next stage?

Use **`final_data/corpus.jsonl` as the loader interface**, after applying and validating
the next cleaning pass. Each line contains one full document. Send only its `text`
field to the chunker; retain `document_id`, `source` and page spans as metadata on
the resulting chunks. JSONL is JSON stored one record per line.

The per-document `.txt` is for readable inspection. The per-document `.json` is the
audit/structure record, containing `pages[].clean_text`, raw text, coordinates and
cleaning diagnostics. Do not embed the entire JSON or accidentally index raw and
clean text together. Do not process `.txt`, `.json` and JSONL as separate copies of
the same document.

**Changing the file extension does not fix the text:** the current JSONL `text`,
per-document text file and concatenated page `clean_text` contain the same cleaned
content, including its present Markdown/fences and defects. The new pass must
regenerate all representations and page offsets together.

## Required work before the research runs

1. Create a consistent indexable representation: validated headings, readable
   paragraphs/list items and explicit table cells/rows. Remove artificial whole-page
   fences without destroying actual code examples or layout semantics.
2. Refine positional page-number/header removal and exclude confirmed blank/noise
   pages from indexed text while preserving their provenance.
3. Resolve line-end word splits, displaced punctuation and spaced decimals using
   source-aware rules. Do not make blanket replacements that damage mathematics,
   legitimate compound words or programming material.
4. Repair multi-column order, merged/continued table headers, mathematical layout
   and image-based evidence. Where reliable conversion is unavailable, explicitly
   exclude the affected evidence from the chosen experimental scope and document it.
5. Re-audit source pages, create a verified question/evidence set, and freeze one
   versioned corpus. Feed the same accepted text to all five chunking strategies.
   Keep extraction defects separate from chunking/retrieval/generation failures.

For now, work on loader interfaces and pipeline plumbing can continue. Comparative
research scores should wait for these repairs and acceptance checks.
